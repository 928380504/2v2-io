# 游戏模板数据库结构与消耗优化规范

本文是浏览器游戏模板的数据库权威规范。它说明哪些数据属于所有游戏都可复用的社区基础层，哪些数据必须由竞赛适配器扩展，以及如何在不牺牲用户体验的前提下控制 Cloudflare D1 读取、写入和 Workers 请求。

凡是新增网站、接入新游戏、修改评论/评分/互动、增加跑马灯或排行榜、调整缓存、增加迁移或优化 SQL，必须先阅读本文和 [COMPETITION-FEED-LEADERBOARD-SPEC.md](COMPETITION-FEED-LEADERBOARD-SPEC.md)。禁止为了快速适配新游戏而绕过预聚合、快照、索引或共享缓存。

## 1. 目标与不变量

模板数据库必须同时满足：

1. 每个网站独占一套 D1，禁止多个游戏站共享同一个数据库。
2. 评论、评分、播放、点赞、踩和收藏属于社区基础层，可以跨游戏类型直接复用。
3. 对局、积分、距离、关卡、时间、连胜、跑马灯和排行榜属于竞赛扩展层，通过适配器表达游戏差异。
4. 页面访问只读聚合表或排名快照，不得反复扫描原始事件。
5. 公共数据允许共享缓存；带访客身份的数据不得进入公共缓存。
6. 普通访问读取快照；只有玩家主动刷新才计算实时排名。
7. 写入必须幂等或有明确限额，客户端重试不能重复累计同一事件。
8. 历史迁移不可回改、改名或重新编号，只能追加新迁移。
9. 数据库优化必须同时记录查询次数、读取行数、写入行数和每访客读取行数，不能只看请求数。

## 2. 分层架构

```text
浏览器与游戏 iframe
  ├─ 页面本地缓存 / localStorage
  ├─ 站点访客 UUID 与游戏本地档案 UUID
  └─ 结构化事件 outbox
          ↓
functions/api 稳定路由包装
          ↓
backend/community            backend/adapters/<adapter>
评论、评分、互动、卡片       对局、跑马灯、排行、奖牌
          ↓                         ↓
       D1 社区表                D1 竞赛表
          ↓                         ↓
聚合统计 / HTTP 缓存          聚合统计 / 排名快照 / 边缘缓存
```

固定边界：

- `functions/api` 只维持稳定 URL，不承载大段 SQL 或游戏专属逻辑。
- `backend/community` 是跨站通用实现。
- `backend/adapters` 隔离游戏竞赛模型。
- `site/data-provider.ts` 声明接口、指标、缓存时间和展示措辞。
- `site/backend.ts` 只选择 D1 绑定名和竞赛适配器。
- `migrations/` 属于单站保护区；模板同步不得覆盖已执行历史。

## 3. 社区基础数据层

基础层由 `community` 迁移组提供，适用于没有排行榜的纯静态小游戏站，也适用于启用竞赛扩展的站点。

### 3.1 评论与回复

| 表 | 作用 | 关键约束/索引 |
| --- | --- | --- |
| `comments` | 评论、回复、根评论评分及可见状态 | `comment_id` 主键；按 `game_id + status + parent_id + created_at` 分页 |
| `comment_daily_usage` | 同一访客每日评论次数 | `(visitor_id, day_key)` 主键；每日最多 3 条 |
| `comment_reactions` | 用户对单条评论的赞/踩状态 | `(comment_id, visitor_id)` 主键 |
| `comment_game_stats` | 每个游戏的评论数、根评论数、评分和、评分票数 | `game_id` 主键；列表和评分禁止回扫全部评论 |

必须保持：

- 评论正文是纯文本，不允许任何链接形式。
- 服务端执行长度、重复内容、轻度负面、自定义辱骂、刷屏和全大写校验。
- 同一访客同一天相同内容使用内容指纹唯一索引去重。
- 回复的 `rating` 必须为 `NULL`；只有根评论贡献游戏评分。
- 新评论写入时同步增量更新 `comment_game_stats`。
- 获取评分时读取 `comment_game_stats`，禁止 `AVG(comments.rating)` 扫描评论表。
- 评论列表包含当前访客的反应状态，因此返回 `no-store`；不能放入公共边缘缓存。
- 批量评分接口一次最多 50 个游戏，并按排序后的规范化游戏 ID 构造稳定请求。

### 3.2 评分

D1 只保存真实评论评分：

```text
rating_sum   = 真实评分总和
rating_count = 真实评分票数
```

公开可见评分和 SEO 结构化评分统一叠加 50 票、每票 5 星的基础权重：

```text
公开分数 = (250 + rating_sum) / (50 + rating_count)
公开票数 = 50 + rating_count
```

禁止：

- 把 50 票基础权重写进 D1，导致重复初始化或迁移叠加。
- 可见评分使用真实数据、JSON-LD 却使用静态目录评分。
- 每次构建与运行时使用不同公式。
- 为了提高评分展示而伪造新的评论记录。

### 3.3 播放、点赞、踩和收藏

| 表 | 作用 | 关键约束/索引 |
| --- | --- | --- |
| `game_engagement_stats` | 每个游戏的播放、点赞、踩、收藏总计 | `game_id` 主键；卡片批量读取只访问该表 |
| `game_visitor_engagement` | 访客的播放时间和兼容状态 | `(game_id, visitor_id)` 主键；按访客查询有索引 |
| `game_engagement_vote_usage` | 每访客、每游戏的点赞/踩真实上传额度 | `(game_id, visitor_id)` 主键；点赞和踩各最多 5 次 |

当前语义：

- 播放：同一访客、同一游戏每 30 分钟最多新增一次真实播放。
- 点赞：每访客、每游戏最多上传 5 次；超过后只保留本地动画反馈。
- 踩：每访客、每游戏最多上传 5 次；超过后只保留本地动画反馈。
- 收藏：采用一次参与式计数，不设计取消后回滚公共计数；客户端负责避免同一浏览器重复提交。
- 未登录访客由站点命名空间下的 UUID 识别，不使用完整 IP 或设备指纹。

卡片数据必须批量查询：

```text
GET /api/games/cards?gameIds=a,b,c
```

禁止每张卡片各发一次请求，也禁止为排序读取 `game_visitor_engagement` 全部访客记录。热门排序只使用 `game_engagement_stats` 的聚合值。

当前全站热度公式：

```text
热度 = 播放量 × 1 + 点赞 × 5 + 收藏 × 50
```

## 4. 竞赛扩展数据层

竞赛层不是把 `wins` 字段替换成另一个名字，而是一套稳定的数据处理流水线：

```text
原始幂等事件
  → 增量玩家周期统计
  → 派生跑马灯事件 / 里程碑
  → 周期榜单快照
  → 公共分页 + 个人快照窗口
  → 少数玩家主动实时刷新
```

新游戏可以改变事件内容和排名指标，但不能绕过这条流水线。

### 4.1 适配器必须定义的内容

- `adapterId`、`gameId`、`modeKey` 和事件结构版本。
- 原始事件的唯一 `eventId`，有单局概念时还要有稳定 `runId`。
- 主排名指标、排序方向和平分规则。
- 日榜周期、总榜周期和站点时区。
- 跑马灯结果事件、里程碑事件和排名事件。
- 是否支持昨日领奖台、历史奖牌、连胜和主动实时刷新。
- 需要的原始字段、聚合字段和索引。

示例映射：

| 游戏类型 | 原始事件 | 聚合主指标 | 排序 |
| --- | --- | --- | --- |
| 1v1 射击 | 一局胜/负、击杀、死亡 | `wins` | 高值优先，再比较胜率等 |
| 文字游戏 | 完成一轮、积分、单词数 | `bestScore` | 最高分优先 |
| 跑酷游戏 | 一次运行、距离、时间 | `bestDistance` | 最远距离优先 |
| 速通游戏 | 关卡完成、耗时 | `bestTimeMs` | 最低时间优先 |
| 生存游戏 | 一次生存、持续时间 | `bestSurvivalMs` | 最长时间优先 |

禁止把文字、跑酷或点击游戏强行塞入 `match_events` 的 `kills/deaths/wins` 字段。应新增适配器迁移和聚合表，同时保持通用 API 响应外壳不变。

### 4.2 1v1 参考实现的表

| 表 | 层级 | 用途 |
| --- | --- | --- |
| `match_events` | 原始事实 | 幂等保存每局结算；`event_id` 主键 |
| `leaderboard_player_stats` | 增量聚合 | 保存日周期和 `__all__` 总周期的玩家统计 |
| `feed_events` | 展示派生 | 保存可直接轮播的 LIVE/STREAK/ARENA 事件 |
| `daily_player_milestones` | 去重状态 | 防止同一玩家、同一日、同一级里程碑重复播报 |
| `daily_podium` | 周期结算 | 保存昨日 1–3 名及获奖时指标 |
| `daily_podium_days` | 幂等结算锁 | 保证每天只累计一次奖牌 |
| `leaderboard_medal_totals` | 历史聚合 | 保存个人历史金银铜和总奖牌数 |
| `leaderboard_snapshot_state` | 快照指针 | 保存周期当前激活快照、生成时间、人数和构建锁 |
| `leaderboard_rank_snapshots` | 排名快照 | 保存某次快照中每位玩家的最终排名和展示数据 |
| `leaderboard_live_refresh_limits` | 实时刷新限额 | 每档案 5 分钟冷却、每日每周期最多 12 次 |

## 5. 事件上传与写入优化

游戏 iframe 使用持久化 outbox：

1. 游戏生成 UUID v4 `eventId` 并把事件写入本地待上传队列。
2. 每批最多上传 20 个事件。
3. 服务端使用 `INSERT OR IGNORE` 或唯一约束幂等写入。
4. 只有真正插入的新事件才能更新聚合统计和生成跑马灯事件。
5. 服务端返回 `acknowledgedEventIds` 后，游戏才从 outbox 删除。
6. 网络重试复用原 `eventId`，禁止重新生成 ID。

国家代码来自 Cloudflare 请求元数据；客户端上报的国家不可信。客户端时间只用于周期归属和展示，服务端同时保存接收时间并校验允许范围。

派生统计必须在写入路径增量维护。禁止在每次榜单请求时对原始事件执行 `GROUP BY profile_id`、窗口函数和全表排序。

## 6. 跑马灯结构与性能

跑马灯查询只读取 `feed_events`，不直接从原始事件临时计算文案、连胜和排名变化。

必须保持：

- `feed_event_id` 稳定且唯一。
- 结果、里程碑和排名事件在写入阶段生成并去重。
- 查询使用 `occurred_at DESC, created_at DESC, priority DESC, feed_event_id DESC` 对应索引。
- 返回最新有效事件，不把“15 分钟刷新”误写成“只查最近 15 分钟”。
- 客户端默认 15 分钟读取一次，首次无缓存立即请求。
- 一次最多返回配置上限，默认 20 条。
- LIVE 数量最多、STREAK 较少、ARENA 最少；展示层按类型配额选择，不能让高频 LIVE 永远淹没其他事件。
- 跑马灯是公共数据，不携带访客 UUID。

若未来跑马灯读取成为 D1 主要消耗，可复用排行榜的规范化 Cache API 模式；不得先通过缩短数据窗口牺牲内容完整性。

## 7. 排行榜快照架构

### 7.1 增量统计而非原始扫描

每个新事件只更新相关玩家的周期统计：

- 日榜使用站点时区的 `YYYY-MM-DD` 作为 `period_key`。
- 总榜使用稳定保留值，例如 `__all__`。
- 排名所需的全部平分字段都应预先保存在统计表。
- 排名索引必须按真实 `ORDER BY` 的字段顺序建立。

### 7.2 快照生成

当前基线：

- 日榜快照 TTL：3 小时。
- 总榜快照 TTL：24 小时，并在新站点日开始后强制产生当天快照。
- 快照构建锁：2 分钟，避免并发首访重复计算。
- 新快照完整写入后才原子切换 `active_snapshot_id`。
- 激活成功后再删除旧快照；失败时保留旧快照。
- 过期但仍可用的快照先返回，后台通过 `waitUntil` 重建。

禁止先删除旧快照再构建新快照，否则中途失败会产生空榜。

### 7.3 公共分页

普通公共请求读取同一个激活快照：

- 默认最多读取前 100 名。
- 额外读取最后一名用于表达总人数。
- 不返回第一名到当前玩家之间的全部数据。

快照表必须保留：

```text
PRIMARY KEY (snapshot_id, profile_id)
UNIQUE INDEX (snapshot_id, rank)
```

查询“排名区间 + 最后一名”时禁止使用以下形式：

```sql
WHERE snapshot_id = ?
  AND ((rank > ? AND rank <= ?) OR rank = ?)
```

该 `OR` 可能使 D1 扫描整个快照。必须拆为两个能独立使用 `(snapshot_id, rank)` 索引的分支，并使用 `UNION ALL` 合并；当最后一名已在分页区间时排除重复行。

### 7.4 个人排名窗口

普通个人窗口不是实时排名。它必须：

- 先按 `(snapshot_id, profile_id)` 定位本人快照排名。
- 再按 `(snapshot_id, rank)` 读取上一名、本人、下一名约 2–3 行。
- 与公共榜单使用同一个 `active_snapshot_id`。
- 本人在前三名时不额外显示个人窗口；第 4 名及以后显示。
- 不进入公共边缘缓存，因为请求包含访客档案 ID。

禁止公共榜单读快照、个人窗口却默认读实时统计；这会造成同一界面名次冲突。

### 7.5 主动实时刷新

只有用户主动点击刷新按钮才允许运行完整实时排名：

- 玩家必须已经参与对应周期。
- 每档案、每周期 5 分钟冷却。
- 每档案、每周期、每天最多 12 次。
- 返回公共前 N 名、最后一名和个人窗口同一份实时结果。
- 成功后同时覆盖页面状态与浏览器缓存，刷新网页不能退回旧快照。
- 实时接口返回 `no-store`，禁止写入公共缓存。

实时查询是保留给少数活跃玩家的高成本能力。不得让首次访问、页面刷新、切换榜单或滚动列表隐式触发实时查询。

## 8. 缓存分层

快照与缓存不是同一件事：

```text
排名快照：避免每次重新计算排名
边缘缓存：避免每个访客都读取同一份快照行
浏览器缓存：避免同一访客重复请求
```

当前缓存基线：

| 数据 | 浏览器配置 | 服务端/边缘 | 个性化 |
| --- | --- | --- | --- |
| 游戏卡片统计 | 15 分钟 | HTTP 300 秒 + SWR 900 秒 | 否 |
| 批量评分 | 15 分钟 | HTTP 300 秒 + SWR 900 秒 | 否 |
| 单游戏互动 | 15 分钟 | `no-store` | 是 |
| 评论列表 | 可视区加载 | `no-store` | 是 |
| 跑马灯 | 15 分钟 | 短期公共响应 | 否 |
| 日榜 | 3 小时快照 | 公共分页使用显式边缘 Cache API | 个人窗口单独读取快照 |
| 总榜 | 24 小时快照 | 公共分页使用显式边缘 Cache API | 个人窗口单独读取快照 |
| 主动实时榜 | 成功后覆盖本地榜单缓存 | `no-store` | 是 |

`Cache-Control` 只声明缓存意图，不能假定 Pages Functions 一定会跨访客共享命中。需要确定降低 D1 读取的公共高成本接口，应显式使用：

```text
caches.default.match(canonicalKey)
caches.default.put(canonicalKey, response.clone())
```

排行榜公共缓存键必须规范化，只包含会改变公共结果的字段：

- 周期：`daily` / `allTime`
- 站点日期：仅日榜
- `limit`
- `offset`
- 必要时适配器/模式和缓存结构版本

禁止把原始查询参数顺序、追踪参数或 `profileId` 混入公共键，导致缓存碎片。禁止把含 `profileId`、用户反应、评论权限或刷新额度的响应写入公共缓存。

Cloudflare Cache API 是按数据中心分布的缓存，不是全球唯一内存。第一次到达某个节点仍可能读取 D1，因此必须同时保留高效索引查询，不能依赖缓存掩盖慢 SQL。

## 9. 索引设计规则

每个高频查询在上线前都必须回答：

1. `WHERE` 的等值字段是什么？
2. 范围字段是什么？
3. `ORDER BY` 顺序是什么？
4. 查询返回多少行、数据库实际读取多少行？
5. 参数组合是否会因 `OR`、函数包装或类型转换放弃索引？

推荐模式：

- 等值分区字段在索引最前，例如 `snapshot_id`、`period_key`、`game_id`。
- 之后放排序或范围字段，例如 `rank`、`created_at`。
- 幂等键使用主键或唯一索引，不依赖先查后写。
- 只对真实高频过滤条件增加索引；每个无用索引都会增加写入成本和存储。
- 对局、评论和活动数据随时间增长时，公共页面不得直接读取无界历史。

禁止模式：

- `SELECT *` 后在 JavaScript 中筛选数千行。
- 为取得本人排名返回从第一名到本人之间全部玩家。
- 卡片列表逐游戏查询。
- 每次评分请求扫描评论正文表。
- 每次跑马灯请求从原始对局重新计算连胜。
- 每次榜单请求从原始事件执行窗口排序。
- 用延长刷新时间掩盖无索引查询。

## 10. 新游戏接入流程

### 10.1 只有基础社区功能

适用于点击、跑酷、休闲单机等暂不需要竞赛排行的网站：

1. 为新站创建独占 D1。
2. 保持 `community` 迁移组。
3. 关闭 `activityFeed`、`leaderboard` 和 `matchEvents`。
4. 运行迁移后即可使用播放、点赞、踩、收藏、评分和评论。
5. 不要创建空的竞赛表或伪造排行数据。

### 10.2 需要跑马灯和排行榜

1. 先确定主指标、周期、排序方向和平分规则。
2. 选择已有适配器；不匹配时创建新适配器，禁止修改 1v1 适配器兼容所有游戏。
3. 定义最小原始事件和幂等键。
4. 设计周期聚合表和完全匹配排序的索引。
5. 设计展示派生事件及里程碑去重表。
6. 设计排名快照、激活指针、构建锁和个人窗口索引。
7. 设计主动刷新资格、冷却和每日限额。
8. 在 `competition-packs/<adapterId>` 声明适配器配置和追加迁移。
9. 使用 `competition:install` 预览并安装，禁止手工复制半套文件。
10. 使用新站独占 D1，从 `community + 当前适配器` 两组迁移建立结构。
11. 验证空榜、少量玩家、超过 100 名、最后一名、跨日、快照过期和主动刷新。
12. 用真实或模拟流量记录每次查询的读取行数。

标准命令：

```text
npm run competition:install -- --list
npm run competition:install -- --adapter <adapter-id>
npm run competition:install -- --adapter <adapter-id> --apply
npm run migrations:list
npm run cloudflare:provision
npm run cloudflare:migrations -- --remote
```

远程应用必须使用部署向导生成的精确确认令牌和 Wrangler 原生迁移追踪。禁止使用 raw `d1 execute` 绕过迁移状态。

## 11. 迁移规则

- 新站数据库从零建立，不迁移其他网站的历史数据。
- `community` 与当前竞赛适配器迁移按全局编号排序执行。
- 已执行迁移禁止回改，即使只是修改索引名称或注释。
- 新字段、索引、回填或清理都追加下一个迁移编号。
- 一个迁移只能归属于一个迁移组。
- 建表使用 `IF NOT EXISTS`，但不能依靠它掩盖不同版本的同名表结构。
- 大规模回填必须评估一次性读取/写入，并避免在普通请求中重复运行。
- 派生快照结构变更后可以清空并重建快照，但不能删除原始事实事件。

## 12. 消耗观测与验收

上线前后至少比较连续 24 小时：

- Workers Standard Requests
- D1 SQL 查询次数
- D1 Rows Read
- D1 Rows Written
- 每条主要 SQL 的执行次数、P50/P99、读取行数和返回行数
- 访客数

必须计算：

```text
每访客读取行数 = D1 Rows Read / 访客数
读取放大倍数 = SQL 读取行数 / SQL 返回行数
```

流量变化时优先比较每访客指标。缓存优化通常显著降低 Rows Read，但不一定降低 Workers Requests；写入逻辑未改变时 Rows Written 也不会同步下降。

排行榜公共快照查询的目标是读取数量接近 `limit + 1`，而不是为返回 100 行读取数千行。若读取放大倍数持续超过 5，应检查索引和查询计划；超过 20 视为必须修复。

1v1 当前优化基准记录在 `template/reports/leaderboard-d1-optimization-baseline-2026-08-20.md`。该报告用于历史对照，不是所有新站的固定额度承诺。

## 13. AI 修改保护规则

后续 AI 在动手前必须先明确本次变化属于：

- 社区基础层；
- 竞赛适配器层；
- 公共 API 契约；
- 缓存策略；
- 数据库迁移；
- 纯展示层。

若无法分类，必须先停止修改并审查架构，不得把 SQL 临时塞入组件或路由包装。

任何排行榜修改都必须证明：

1. 普通公共榜单读取快照。
2. 普通个人窗口读取同一快照。
3. 只有主动刷新运行实时排名。
4. 分页与最后一名使用索引友好查询。
5. 公共缓存键不包含个人身份。
6. 缓存失效时 SQL 本身仍然高效。
7. 快照构建有并发锁、原子激活和失败回退。
8. 日榜、奖牌和站点时区使用统一边界。

任何基础互动修改都必须证明：

1. 卡片统计使用批量接口和聚合表。
2. 评论/评分不回扫无界数据。
3. 写入有限额或幂等键。
4. 个性化响应不进入公共缓存。
5. 公开评分与 SEO 使用同一基础权重公式。

## 14. 发布验收清单

- [ ] 新站使用独占 D1。
- [ ] 只选择 `community + 当前适配器` 迁移。
- [ ] 所有历史迁移保持不变，新结构使用追加迁移。
- [ ] 游戏事件具有稳定幂等 ID，批量上限不超过 20。
- [ ] 页面公共统计来自聚合表，不扫描原始记录。
- [ ] 卡片和评分使用最多 50 个游戏的批量接口。
- [ ] 评论每日限额、重复检测和纯文本审核有效。
- [ ] 点赞和踩的每访客上传上限有效。
- [ ] 播放冷却有效。
- [ ] 跑马灯读取派生事件，首次无缓存能自动加载。
- [ ] 日榜和总榜读取快照，个人窗口与公共榜单同源。
- [ ] 主动实时刷新具备资格、冷却和每日限额。
- [ ] 快照分页使用 `(snapshot_id, rank)` 索引且无扫描型 `OR`。
- [ ] 公共排行榜显式使用边缘共享缓存。
- [ ] 个性化和写入响应使用 `no-store`。
- [ ] 已验证空数据、少量数据、大于 100 名和跨日行为。
- [ ] 已记录部署前后每访客读取行数和读取放大倍数。

本文与竞赛 UI/事件契约规范共同构成模板数据库的稳定边界。游戏可以更换，指标可以更换，页面主题可以更换，但预聚合、快照、索引、缓存、幂等和可观测性不能被重新发明。
