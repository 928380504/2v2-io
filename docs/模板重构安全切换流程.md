# 模板重构安全切换流程

本文用于将一个已经完成大幅重构的新站点安全替换为 GitHub 仓库的 `main`。适用于“新版本无需与旧代码逐文件合并，只希望先通过分支测试，确认后直接成为正式版本”的场景。

## 核心原则

1. 不在旧 `main` 上反复覆盖和合并新结构。
2. 新版本先作为独立迁移分支部署到 Cloudflare Pages Preview。
3. 新提交必须直接以旧 `main` 为父提交，保证可以快进切换。
4. Preview 验证通过后，把迁移分支直接快进到 `main`。
5. 不创建合并提交，不使用 `git push --force`。
6. 切换前必须创建并推送恢复标签。
7. 正式切换后，以“源网站”目录作为唯一日常工作目录。

## 本次采用的目录

- 正式仓库目录：`H:\项目资料\海外网站\源网站\1v1-lol`
- 迁移原稿目录：`H:\项目资料\海外网站\迁移站点\1v1-lol`
- 临时发布工作树：`H:\项目资料\海外网站\迁移站点\1v1-lol-release`

后续修改只在正式仓库目录进行。迁移原稿用于归档和参考，不再作为上传目录。

## 一、切换前检查

在正式仓库目录确认：

```powershell
git status --short
git branch --show-current
git rev-parse HEAD
git rev-parse origin/main
```

必须满足：

- 当前分支是 `main`。
- 工作区没有未提交修改。
- 本地 `main` 与远程 `origin/main` 一致。
- 已记录旧版 `main` 的完整提交号。

如果工作区不干净，先判断修改属于谁并妥善提交或保存，禁止直接清除。

## 二、建立可恢复锚点

为旧版正式站创建恢复标签：

```powershell
git tag pre-template-2.0-YYYYMMDD <旧版-main-提交号>
git push origin pre-template-2.0-YYYYMMDD
```

标签必须推送到 GitHub。只保存在本地无法防范本机目录损坏或误操作。

本次实际恢复标签：

```text
pre-template-2.0-20260818
```

## 三、创建独立迁移分支和工作树

迁移分支应从旧 `main` 创建：

```powershell
git branch migration/template-2.0 <旧版-main-提交号>
git worktree add "H:\项目资料\海外网站\迁移站点\1v1-lol-release" migration/template-2.0
```

这样做的作用：

- 原正式目录保持不动。
- 新版可以在独立目录构建、提交和部署。
- 迁移提交会直接成为旧 `main` 的下一代提交。
- 最终可以快进切换，不需要合并两套完全不同的目录结构。

## 四、复制迁移版本

把迁移原稿复制到临时发布工作树，但必须排除：

```text
.git
.next
.wrangler
node_modules
out
backups
.env*
next-env.d.ts
tsconfig.tsbuildinfo
template/reports
template/sites.json
```

注意事项：

- `.git` 只能保留工作树自己生成的 Git 元数据。
- `.env*` 不得进入仓库。
- 构建产物和依赖目录应重新生成。
- 复制完成后应比较源文件与目标文件的数量和哈希，确认没有缺失、额外或内容不一致。

## 五、完整验证新版

在临时发布工作树依次执行：

```powershell
npm clean-install
npm exec tsc -- --noEmit
npm run build
npm run template:verify
npm run site:create
npm run site:export
```

还应执行仓库中已有的测试命令。验证标准包括：

- 依赖安装成功。
- TypeScript 类型检查通过。
- Next.js 静态构建成功。
- Pages Functions 正常生成。
- 模板版本和核心文件校验通过。
- 游戏数量、主游戏和域名配置正确。
- 构建后 Git 工作区仍可解释，不包含意外产物。

## 六、形成单一替换提交

确认新版完整后，在迁移分支创建一个清晰的替换提交：

```powershell
git add -A
git commit -m "Replace site with game template 2.0"
```

随后验证迁移提交的父提交就是旧 `main`：

```powershell
git rev-parse HEAD^
git merge-base --is-ancestor origin/main HEAD
```

第二条命令返回成功，才说明能够安全快进。

## 七、先发布 Preview

推送迁移分支：

```powershell
git push -u origin migration/template-2.0
```

等待 Cloudflare Pages 为该分支生成 Preview 域名，然后至少检查：

- 首页。
- 分类页。
- 标签筛选页。
- Hot Games 页面。
- 主游戏内页。
- `/api/health`。
- D1 绑定和竞赛适配器。
- 关键移动端布局与交互。

本次健康接口成功响应示例：

```json
{
  "ok": true,
  "database": "ready",
  "competitionAdapter": "1v1-lol"
}
```

Preview 未通过时，只继续修改迁移分支，禁止切换 `main`。

## 八、直接快进切换 main

Preview 验证通过后，重新确认远程 `main` 没有在测试期间产生新提交：

```powershell
git fetch origin
git rev-parse origin/main
git merge-base --is-ancestor origin/main migration/template-2.0
```

确认无误后执行：

```powershell
git push origin migration/template-2.0:main
```

这条命令会让 `main` 直接前进到迁移提交：

- 不创建合并提交。
- 不把两套目录进行内容合并。
- 不改写旧历史。
- 不需要强制推送。

如果 Git 拒绝推送，说明远程 `main` 已发生变化或无法快进。此时停止操作并重新核对，禁止改用 `--force` 强行解决。

## 九、同步正式工作目录

切换成功后，在正式仓库目录执行：

```powershell
git pull --ff-only origin main
```

然后核对：

```powershell
git rev-parse HEAD
git rev-parse origin/main
git status --short
```

必须满足：

- 本地 `HEAD` 与 `origin/main` 完全一致。
- 工作区干净。
- 正式仓库目录已经是迁移后的新版结构。

## 十、验证生产部署

等待 Cloudflare Pages 的 Production 构建成功，再检查正式域名：

```text
/
/1v1-lol-games
/1v1-lol-games/1v1-lol
/shooting-games
/hot-games
/api/health
```

页面应返回 HTTP 200，健康接口应显示数据库和适配器正常。只有构建成功并通过正式域名验证，切换才算完成。

## 十一、异常回滚

如果新版上线后出现严重问题，可从恢复标签建立回滚分支：

```powershell
git switch -c rollback/pre-template-2.0 pre-template-2.0-YYYYMMDD
git push -u origin rollback/pre-template-2.0
```

先让回滚分支生成 Preview 并验证。如果必须恢复正式站，优先创建一个“恢复旧版内容”的新提交，再快进推送到 `main`，保留完整历史。

不要直接执行：

```text
git reset --hard
git push --force
```

除非已经明确接受改写远程历史的风险并完成额外备份。

## 十二、完成后的目录约定

切换完成后统一遵循：

| 用途 | 目录 |
| --- | --- |
| 日常修改、测试、提交和上传 | `H:\项目资料\海外网站\源网站\1v1-lol` |
| 模板框架自身迭代 | 游戏模板 2.0 主目录 |
| 迁移原稿、对照和归档 | `H:\项目资料\海外网站\迁移站点\1v1-lol` |
| 临时发布工作树 | 验证完成后可移除，不作为日常目录 |

禁止同时在“源网站”和“迁移站点”修改同一个站点，否则会再次形成两个不一致的版本。
